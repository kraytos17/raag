# Contributing to Raag

Thanks for your interest in Raag! This project is a LAN-only P2P music player written
in Go. This guide covers how to set up a development environment, run the checks, and
get a change merged.

## Development setup

Prerequisites:

- Go 1.26+
- `libasound2-dev` (Linux, for audio playback)
- `ffmpeg` (optional, for cross-codec P2P transcoding)

```bash
# Fork and clone
git clone https://github.com/<you>/raag.git
cd raag

# Install pinned dev tools (gofumpt, goimports, golangci-lint, gosec,
# govulncheck, air, buf, protoc-gen-go, goreleaser, trivy) and tidy deps
make dev-setup

# Verify the build
make build
```

`make install` is idempotent and pins known-good tool versions; `make dev-setup` runs
`install` + `deps` + `generate`.

## Project layout

```
cmd/raag       CLI client (play, pause, queue, lib, playlist, peers, tui, ...)
cmd/raagd      Daemon: config, services, startup, daemon lifecycle
internal/app   Application services: playback controller, FSM, scanner, search, resolver
internal/config     Viper-based TOML configuration + defaults
internal/domain     Core domain types, events, sentinel errors, IPC protocol version
internal/convert    Domain <-> protobuf conversion
internal/infra      Infrastructure: audio, ipc, p2p, events, storage, hashing, fsroot, wire
internal/ui/tui     Bubble Tea terminal interface
proto/raag.proto    Source of truth for the IPC + P2P wire protocols
proto/gen           Generated protobuf code (do not edit; run make generate)
```

## Building and running

```bash
make build              # ./bin/raag and ./bin/raagd
make run-daemon         # run raagd in the foreground
make run-cli            # run raag (TUI) against a running daemon
make daemon-start       # daemon in background (Ctrl-C stops it)
make daemon-start-detach
make daemon-stop
make daemon-status
```

Typical workflow while iterating:

```bash
./bin/raagd --music-path ~/Music   # or `raagd --setup` on first run
./bin/raag tui
```

## Quality gates

Run the full pipeline before submitting a PR:

```bash
make ci
```

`make ci` runs, in order:

1. `lint-format` — `gofumpt -l .` and `goimports` drift check
2. `lint-go` — `go vet ./...`
3. `lint-golangci` — `golangci-lint run ./...`
4. `go test -race ./...`
5. `go build` of both binaries into `bin/`

Individual checks:

```bash
make lint        # format + vet + golangci-lint
make sec         # gosec + govulncheck + trivy
make test        # go test -v -race -cover ./...
make test-short  # go test ./...
```

**Baseline:** `golangci-lint` currently reports only deferred `errcheck` findings
(≈50, mostly test files and intentional ignored returns). Do not introduce new lint,
vet, format, or staticcheck issues. Keep `make sec` findings at or below the current
baseline; new code should not add G115/G304-style findings without a `//nosec` +
justification.

## Testing

- Unit tests live next to their package (`foo.go` → `foo_test.go`).
- **Concurrency** — packages that start goroutines (`internal/app`,
  `internal/infra/events`, `internal/infra/p2p`) verify goroutine-leak freedom with
  `goleak.VerifyTestMain`. Keep that wiring in place.
- **Virtual time** — `internal/infra/p2p/node_test.go` uses `testing/synctest` for the
  ticker loops; prefer it over real `time.Sleep` waits for timing-sensitive tests.
- **Filesystem safety** — `internal/infra/fsroot` tests cover symlink-escape and
  out-of-root refusal; the scanner and stream handler depend on this.
- Run a focused suite while developing:

```bash
go test ./internal/app/...
go test ./internal/infra/p2p/...
go test ./internal/infra/fsroot/...
```

## Code style

- **Format:** `gofumpt` (tighter than `gofmt`). `make lint-fix` will auto-fix format
  and golangci issues.
- **Imports:** grouped stdlib → third-party → `github.com/p-society/raag/...`, managed
  by `goimports`.
- **Idioms:** `any` (not `interface{}`), `slices`/`maps` stdlib packages, `errors.AsType`,
  `slog` for structured logging, `wg.Go` for waitgroup-spawned goroutines, `min`/`max`
  builtins where they read as comparisons.
- **Comments:** explain *why*, not *what*. Do not add license headers to every file.
- **No generated edits:** `proto/gen/` is generated by `make generate` (buf); never
  edit it by hand.

## Dependency hygiene

- Keep `go.mod`/`go.sum` tidy: `make deps` (`go mod tidy` + `go mod verify`).
- Do not bump the pinned ecosystem versions (libp2p, quic-go, webtransport-go) without
  a deliberate reason — they are pinned to known-good combinations.
- New dependencies should be justified in the PR description.
- `dependabot` opens weekly PRs for gomod / GitHub Actions / Docker updates; keep those
  grouped and review the pins.

## Commit guidelines

- Small, focused commits. One logical change per commit.
- **Conventional Commits are enforced by CI** (PR titles via
  `action-semantic-pull-request`). They drive the auto-generated release
  changelog (git-cliff/goreleaser), so use them for commits and PR titles:
  - `feat:` new capability
  - `fix:` bug fix
  - `perf:` performance improvement
  - `refactor:` code change with no behavior change
  - `docs:` documentation only (skips most CI via the `[docs only]` marker)
  - `security:` security fix/hardening
  - `test:` test-only change
  - `deps:` dependency bump (dependabot uses this prefix)
  - `ci:` CI/workflow change
  - `build:` build system / Makefile / Docker change
  - `chore:` other maintenance
  Example: `feat: add volume persistence`, `fix(ipc): serialize conn writes`.
- Reference the motivating issue/PR number when applicable.
- Do not commit `bin/`, `coverage.out`, `raagd.log`, `raagd.pid`, or local config/data.

## Pull request process

1. Create a branch: `git checkout -b fix/describe-the-change`.
2. Make the change with tests.
3. Run `make ci` locally; it must pass.
4. Push and open a PR against `main`.
5. In the PR description: what changed, why, how it was tested, and any trade-offs.
6. Keep PRs reviewable — split large features into sequential commits or separate PRs.

If you change the wire protocol (`proto/raag.proto`), run `make generate` and include
the regenerated `proto/gen` in the same PR.

## Getting help

Open an issue for bugs or feature requests, or ask in the PR itself.
